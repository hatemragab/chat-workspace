# Log delivery fix and verification — 17 October 2026

The measured quiet-file delay came from Vector's file reader. Its hardcoded idle gate could leave an already-known input unread for about ten seconds. The local collector now uses a separately built, pinned Vector patch that detects appended bytes and caps idle polling at 250 ms. In the controlled six-source quiet-file comparison, collection changed from **5,467 ms per source** to **106–163 ms**. Flutter now starts normal export after 100 ms and flushes a full batch or critical record promptly.

Important diagnostics now have reserved capacity, automatic retries, stable delivery identity and explicit loss/uncertainty counters. Two independent Flutter Web sessions survived a **58.551-second API and collector outage**, subsequently exported their ten error records, and displayed **all 100 distinct burst messages** in each UI. Their final exporter snapshots report **zero dropped important/critical records and no pending records**. This is bounded recovery evidence, not a promise of losslessness through arbitrary outages or process death.

The actual provided-MCP review traversed **293 sequential pages requested with limit 50** across a fixed main interval and a post-fix addendum, covering **14,598 new acceptance records** through **13:45:50.778 UTC**. Healthy current-browser collection in the main interval measured **p50 116 ms, p95 502 ms, maximum 636 ms**; the final collector's separate healthy sample measured **258 / 674 / 763 ms**, excluding restart backlog. Both show subsecond healthy delivery in the tested window, replacing the observed roughly eleven-second delay. All ten browser error identities reached the capture once; **all 9,148 records acknowledged by the latest two inspector snapshots are present once**, with only 15 explicitly sampled noise gaps. All 305 warning/error observations are classified, including the three deliberate final severity fixtures. Final readbacks confirm all eight service roles ready, both clients sharing and all five sources visible in live Logdy. No commit, push, log reset or database/media purge was performed for this follow-up.

All technical timestamps below are UTC for direct comparison with the capture; Cairo is UTC+3 on this date. This report supersedes the delay/loss limitations in [the earlier fix report](SYSTEM_FIX_REPORT_2026-10-17.md) only where new evidence is provided.

## Cause, fix and reproducible build

A timing-only baseline over the latest 2,000 already-emitted Flutter records separated producer batching from collection:

| Stage              |      p50 |      p95 |   Maximum |
| ------------------ | -------: | -------: | --------: |
| Producer → ingress |   431 ms |   755 ms |  1,385 ms |
| Ingress → Vector   | 1,071 ms | 9,547 ms | 10,184 ms |
| Producer → Vector  | 1,437 ms | 9,936 ms | 10,706 ms |

The [pinned official Vector file-watcher source](https://github.com/vectordotdev/vector/blob/a3231c76bdea5078bc54c205cf89f5a1ceddbb73/lib/file-source/src/file_watcher/mod.rs) enters a hardcoded ten-second read gate after ten seconds without a successful read. Its parent scheduler also permits a 2,048 ms idle sleep. Changing discovery cooldown alone cannot wake this already-known quiet file.

The patch checks the open plain-file descriptor's size when the old gate would skip it, avoids payload reads at unchanged EOF, and caps idle polling at 250 ms. Discovery of replacements/new inputs also uses 250 ms. Existing fingerprints, read positions, checkpoints and rotation remain in use. The periodic fallback remains for metadata errors and compressed inputs. There is no second tailer or artificial heartbeat log.

The official downloaded Vector binary remains intact. Collector startup and install/verify select a separate source-built artifact and verify its provenance; they never silently fall back to the slow binary. The minimal build enables only `sources-file,sinks-file,transforms-remap`; the unsupported `api` configuration field is omitted because that build has no API feature.

The actual build tree's **4,316 upstream source files** match a fresh pinned extraction plus the exact patch, with zero mismatches. The build recipe pins downloads, checks sizes/hashes, uses two Cargo jobs, tests the watcher and verifies the output. This is a reproducible input recipe, not a bit-identical build claim across arbitrary hosts.

After 13 seconds of silence, the unpatched installed-binary fixture collected each of six streams in **5,467 ms**. The patched fixture measured **106, 106, 136, 148, 148 and 163 ms**. These streams cover backend, service diagnostics, Flutter and native Redis/MongoDB/Centrifugo. ## Important-record preservation

| Layer                       | Implemented behavior                                                                                                                                                                                                                                                                                                                                             | Finite boundary                                                                                                                                                                                           |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend structured logger   | Warn/error, aborted/failed operations and HTTP/provider status ≥400 receive a separate 1 MiB reserve beyond the ordinary 4 MiB queue. They can evict queued ordinary records, preserving survivor order and the in-flight entry. Automatic append/open retries retain stable `logRecordId`, attempt and previous-outcome metadata.                               | At most 30 seconds and 32 actual append attempts. Important-only exhaustion, unsafe/permanent failure and expiry explicitly count important loss.                                                         |
| Owned native/process writer | Same 4 MiB ordinary + 1 MiB important policy and automatic finite retry. Structured JSON severity is authoritative; plain-text severity words are fallback. Merely appearing on stderr does not make a record an error.                                                                                                                                          | The same retry and capacity limits apply. Raw private launcher output is not automatically imported into the sanitized unified capture.                                                                   |
| Partial append recovery     | Failed descriptors close. Reopening fences any ambiguous partial line with a newline before the next complete record. Known zero-write failures and uncertain partial/full-write acknowledgements are distinguished.                                                                                                                                             | An ambiguous append may replay; stable record ID and delivery-attempt metadata identify it. This is at-least-once recovery, not exactly-once delivery.                                                    |
| Mongo operation diagnostics | Pending identity remains bounded at 4,096 operations / 60 seconds. Capacity/age/pool-close/shutdown omissions produce coalesced warning summaries, at most four per second. A later unmatched failure remains visible with unknown identity and `correlationUnavailable=true`.                                                                                   | Omission accounting preserves the fact and available safe metadata, not expired query details or invented correlation.                                                                                    |
| Flutter operation spans     | The 64-span bound now limits optional DevTools tracking only. Every caller-owned operation still gets a bounded-data handle and its begin/end pair, including terminal failures. Epoch/session/privacy fences apply to overflow handles.                                                                                                                         | No unbounded inspector-owned overflow collection. Registry degradation is exposed as `overflowSpans`; it no longer silently removes operation records.                                                    |
| Flutter export              | Normal first flush 100 ms; full 50-record batch/critical event requests immediate flush. One request at a time, 50 records / 256 KiB, two-second request timeout. Transport/408/429/5xx retries retain identical serialized batch and UUID, at 100 ms, 500 ms, one second, then at most two seconds while active.                                                | Queued payload ≤500 records / 1 MiB plus one retained/in-flight batch ≤50 / 256 KiB. Combined encoded payload ≤550 records / 1.25 MiB, excluding framing/object overhead.                                 |
| Flutter priority            | All operation begin/end records are operational or critical. Critical includes safe error type, explicit warn/error severity, status ≥400 or failed outcome. Critical reserves 50 slots / 256 KiB; noncritical admission is bounded at 450 / 768 KiB. Important records evict widget/watch noise first; new ordinary/noise cannot evict queued critical records. | Only instant widget-build/watch observations are pressure sampled. Critical may evict older operational records under saturation; important-only overflow and permanent rejection count explicit loss.    |
| Ingress acknowledgement     | Optional UUID `batchId` is backward compatible with legacy batches. Complete append precedes acknowledgement. Concurrent exact retries share the write; already-accepted exact retries reuse the receipt. Same identity/different content returns 409.                                                                                                           | Receipts last two minutes, at most 16,384. Full unexpired receipt capacity returns retryable 503 rather than evicting evidence. Restart/expiry/ambiguous partial write can still replay physical records. |

Existing backend publication `data` is preserved exactly. Delivery metadata is mirrored into MCP-visible `data.logDelivery` only for backend traffic records that originally had no own `data` field; backend-client Mongo/Redis/Centrifugo metadata preserves data absence. Native normalized records expose only validated delivery identity. Payloads, tokens, message drafts, SQL arguments and arbitrary native attributes were not added to inspector metadata.

The [official Zalando REST guideline preflight](https://opensource.zalando.com/restful-api-guidelines/) was refreshed on 17 October before the compatible loopback-ingress change: [protection (104)](https://opensource.zalando.com/restful-api-guidelines/#104), [compatibility (106)](https://opensource.zalando.com/restful-api-guidelines/#106), [timezone timestamps (169)](https://opensource.zalando.com/restful-api-guidelines/#169) and [private standard problem responses (177)](https://opensource.zalando.com/restful-api-guidelines/#177). The optional batch identity preserves legacy input. This is a local developer boundary, not a production compliance claim; MCP is not a REST API.

The 500-record inspector ring remains a bounded UI view. Its evictions after export are distinct from exporter loss. Priority does not turn this debugging system into a durable audit journal: explicit pause/off/clear/dispose retires sharing, and browser reload has no persistent exporter outbox. Those privacy decisions remain authoritative.

Regression tests preserve **174 concurrent operations / 348 begin/end records**, including 110 tracking-overflow handles and a terminal error. Tests also inject queue pressure, critical-only overflow, temporary disk failure, partial append, rejected acknowledgement after full append, retry expiry, permanent poison batches, no-new-event retry, exact batch identity and caller-data immutability. Disk fault injections use private temporary fixtures, never shared live service data.

# Chat backend

Development listens on `0.0.0.0:3000` so a physical Android device can reach the development machine through its LAN address. Set `HOST=127.0.0.1` for loopback-only access; non-development defaults remain loopback. Centrifugo client connections also need LAN port 8000, while its diagnostics stay on loopback port 9000.

NestJS REST commands and recovery, MongoDB replica-set transactions, latest-room Redis deltas, and user-restricted Centrifugo publications implement the approved root specifications. There is no per-message event log or outbox.

Requires Node.js 22 or newer, local MongoDB configured as replica set `rs0`, Redis, and Centrifugo v6. No Docker is used. Install dependencies with `npm install`, copy `.env.example` to a private `.env`, and fill in fresh JWT credentials plus the secrets already configured in your local Centrifugo. Never include `.env` in source control.

Run `npm run build` then `npm start`, or use `npm run start:dev` to execute the TypeScript entrypoint. The default API address is `http://localhost:3000`. `GET /health` checks MongoDB and Redis. Swagger UI is available at `/docs`, with the self-contained OpenAPI description at `/docs-json`.

In development, startup seeds five debug users and `/auth/debug-users` plus `/auth/debug-login` allow switching accounts. Those routes return 404 outside `NODE_ENV=development`; normal signup/login remain available. Authenticated endpoints require `Authorization: Bearer <accessToken>`. Debug accounts have random unusable passwords. Startup creates missing approved indexes and never drops existing indexes or application data. Mongoose automatic indexing is disabled; `DatabaseService.onModuleInit()` is the single awaited index-initialization path, and index failures prevent startup.

Use the repository's [Centrifugo v6.9.7 local configuration and runbook](../centrifugo/README.md). NestJS loads dedicated realtime credentials from `../centrifugo/.env` before `.env`. The authenticated internal API is on `127.0.0.1:9000/api`; client WebSockets use port 8000. Connection-data JWTs are verified by the loopback/key-protected NestJS connect proxy and become server-side inbox subscriptions. Client subscribe/publish/presence/history/RPC remain unauthorized; history/recovery are disabled. Centrifugo uses the login's actual expiry for native connection expiration, and NestJS disconnects retired sessions with persistent retries. Periodic refresh callbacks are disabled; reconnects validate the session again. Explicit origins match API CORS.

Each user subscribes to exactly `inbox:user#<userId>`. Publications have `{pts,epoch,room}` with the full room and optional updated message. REST responses reconcile resources but clients must advance their local inbox cursor only through serialized socket/delta reconciliation. Message writes and account/room revisions commit together; Redis Lua prevents older requests overwriting newer snapshots. Delta consistency checks force a full snapshot during cache lag or missing room states. Publication failures exhaust three retry attempts, retain REST recovery, and never turn a committed mutation into a failed send. A process interruption between MongoDB commit and Redis update is recovered through the MongoDB revision fence and a full sync.

### Sequenced receipt cutover

New sends allocate a positive `messageSeq` from the room's counter in the same MongoDB transaction as message creation and inbox revisions. A partial unique `(roomId,messageSeq)` index protects allocation; an idempotent retry returns the original sequence. Existing messages remain `messageSeq:null` (including documents without the field); no history is deleted, renumbered or backfilled. Persisted `deliveredAt`/`seenAt` dates remain actual server action dates.

Room projections add `headSeq`, `contentPts`, `ownDeliveredSeq`, `ownSeenSeq`, `peerDeliveredSeq` and `peerSeenSeq`. `contentPts` advances only on message creation/edit/deletion; receipts still advance `msgPts`. Own cursors are acknowledgement checkpoints, peer cursors describe outgoing sequenced-message status. They never certify dates or nullable legacy messages. Own checkpoint changes do not produce a separate push; they are returned by receipt commands and read authoritatively by the next message snapshot. Redis may conservatively lag that optimization until the next hydrated room change.

Existing delivered/seen routes accept additive `{upToSeq}` mutually exclusively with `upToTimestamp`. Sequence boundaries must be safe nonnegative integers at or below the committed head; out-of-range boundaries return 400. Delivery affects only positive-sequence messages. Seen is a room-level read: it also acknowledges pre-cutover nullable legacy incoming rows, preserving their existing non-null dates; if legacy dates change, the publication remains hydrated for legacy reconciliation. Delivery batches support `{targets:[{roomId,upToSeq}]}` (1–100 unique rooms), mutually exclusively with the legacy `{roomIds,upToTimestamp?}` body. All membership/boundary checks precede writes and the entire batch remains atomic. Seen fills missing delivery and clears only the acknowledged unread portion; sequenced messages after the boundary keep their badges. No-op commands publish no peer receipt. Responses add `{rooms:[{roomId,ownDeliveredSeq,ownSeenSeq}]}`; clients may reconcile these checkpoints without moving the inbox cursor.

Every message page adds a same-snapshot `receiptState` with the four cursors and `coverage:{roomPts,msgPts,contentPts,lastHistoryEditPts,headSeq,fromSeq,throughSeq}`. The inclusive coverage interval certifies that every visible sequenced message in that interval was returned. Hidden sequences require no body; `fromSeq=throughSeq+1` is an empty interval. Chronological pagination can diverge from sequence order, so the server finds the largest omitted visible sequence rather than inferring coverage from the largest returned message. Clients join adjoining verified intervals starting at their acknowledged checkpoint before acknowledging a higher delivery sequence; `headSeq` alone is never proof of downloaded bodies. Latest-page legacy timestamp summaries retain their existing shape and gap checks. Nullable legacy rows use exact page dates and existing legacy recovery, never sequence-derived fabricated dates.

`RECEIPT_PUSH_MODE=legacy` is the default and retains hydrated publications. Rooms advertise `receiptProtocol:legacy`; sequence receipt commands return 400 in that mode, and upgraded clients use the legacy timestamp API until coordinated cutover. Compact mode advertises `receiptProtocol:sequence`. After all active clients support the new union, explicitly select `compact` for coordinated rollout. Sequence-only peer receipts then publish `{pts,epoch,receipt:{roomId,eventType,peerDeliveredSeq,peerSeenSeq,contentPts}}`, without room/message content. Clients derive `roomPts=msgPts=pts`, preserve metadata/order, and apply cursor/status changes atomically through the existing inbox queue. Legacy timestamp peer receipts and content events remain hydrated. In compact mode, existing direct/group unread changes publish `{pts,epoch,unread:{eventType:"room_unread_cleared",roomId,unreadCount,ownDeliveredSeq,ownSeenSeq}}`. The count may stay positive after a bounded read. This patch updates only the account badge, own checkpoints and `roomPts=pts`; clients preserve `msgPts`, `contentPts`, history/order, message rows, previews and exact dates. It never changes outgoing peer ticks. The serialized inbox queue applies it and cursor progress atomically, using existing gap/unknown-room recovery. No new own-progress-only events or counters are added; unchanged unread counts remain silent. Redis continues storing the full room snapshot for offline recovery. A sequence-only hydrated event carries `sequenceReceipt:true`, so upgraded clients never apply its timestamp to nullable legacy rows. Revert the configuration to restore hydrated publications; never enable compact while old clients expecting only `room` remain active. Redis always retains full hydrated snapshots for offline/gap recovery.

For an edit or global deletion whose original is hidden from a recipient, the payload omits `updatedMessage`. If that recipient still has a visible reply to the original, optional `quoteUpdate` carries the existing reply snapshot shape, with text capped at 120 characters and deleted image URLs cleared. Clients update matching visible quotes without inserting or resurfacing the original. A recipient without a visible matching quote receives no quote content.

`POST /messages` accepts exactly one of `roomId` and `peerUserId`; a direct room is created only on its first send. Idempotency is scoped to the sender. Preferences preserve message revision and room order. Reader badge clearing and sender delivery/seen events remain separate. When clients supply a receipt boundary, the publication `actionTimestamp` is that boundary, preventing later cached messages from receiving premature ticks; persisted receipt dates record the actual server action time.

The latest direct-room `GET /rooms/:roomId/messages` page includes `receipts: {deliveredThrough, seenThrough, hasGaps}` from the same MongoDB snapshot as membership and message rows. Boundaries are the maximum **message creation timestamps** of the caller's outgoing messages with actual persisted receipts, or `null`; they are not the receipt action time or the peer's outgoing messages. This recovers ticks across retained older history after Redis coalesces a receipt into a later preference. `hasGaps` is true if an unacknowledged outgoing message falls at or before either boundary, such as a concurrently committed timestamp tie. Clients must reset older history and use exact page receipts in that case. Groups and older cursor pages omit the summary. Preference fields may be omitted, but explicit `null` for `pin` or `isMuted` returns 400 before any state or revision changes.

Users and debug-user lists are JSON arrays. Auth returns `{user,accessToken,centrifugoToken}`; send/edit/delete return `{message,room}`; group creation/preferences return `{room}`. Image uploads use multipart field `file`, enforce 5 MiB and supported MIME/signature checks, and return `{imageUrl}`. Generated files live in ignored `public/uploads/`.

Presence uses Centrifugo as its sole connection-status authority. Bounded GET/POST `/presence/status` returns self/shared-room contact snapshots through one server API batch, with 503 on unavailable provider data. There are no application Redis presence leases, due-user index, transition publications or polling worker. Guarded no-body `POST /presence/heartbeat` remains a deprecated no-op for compatibility. `/presence/offline` revokes the login's API/token access and disconnects only that login's realtime clients; repeated releases are idempotent and other connected logins remain online. Redis room projections, rate limits and session revocations remain enabled. See the [presence and diagnostics contract](../centrifugo/README.md).

## Request logs and correlation

The [local Vector pipeline](../LOCAL_OBSERVABILITY.md) feeds Logdy and the existing read-only MCP from one shared capture. It adds independent metadata-only Redis/MongoDB/Centrifugo client diagnostics via `LOCAL_SERVICE_LOG_FILE` (defaulted by `start:dev` and `start:debug`). Flutter inspector export and native server log files join through Vector; no application endpoint or message event log is added. `npm run logs:collector` starts only the local collector, and a running API needs a manual restart to load instrumentation.

Every HTTP request receives `X-Request-ID`. A caller may send a correlation ID containing 1-64 letters, digits, dots, underscores or hyphens; invalid or oversized values are replaced with a generated UUID. Problem JSON includes the same `requestId`, and browser clients can read the exposed response header. OPTIONS preflights are excluded from traffic logs. The structured completion record contains `timestamp`, `level`, `event`, `source`, `requestId`, `userId`, `method`, matched route template, `status`, `durationMs`, and `aborted`. `userId` is the authenticated guard identity, or the trusted returned user for successful login/signup; anonymous and rejected authentication use `null`. Unmatched routes use `[unmatched]`. Responses with status 400+ log at `warn`, and 500+ or aborted responses log at `error`.

`DebugTrafficLogger` is the shared local service for HTTP and realtime traffic. Set `DEBUG_TRAFFIC_LOGGING_ENABLED=true` to add full parsed `params`, `query`, `requestBody`, `responseBody`, `requestHeaders`, `responseHeaders` and the request path to HTTP records. JSON arrays and message content are retained without a preview limit. Multipart uploads and binary/streamed responses use file/type/size metadata instead of raw bytes. Passwords, tokens, authorization, cookies, API keys and other credential fields are recursively redacted. Payload snapshots do not modify the actual request or response. Both development launch commands enable full debug logging by default, while explicit shell or `.env` settings take precedence; `HTTP_LOGGING_ENABLED=false` independently suppresses HTTP completion records while preserving correlation and realtime debug logging.

With debug traffic enabled, each Centrifugo publish attempt emits `event: "realtime_publication"`, `direction: "publish"`, the UTC timestamp, causative HTTP `requestId`, actor `userId`/`actorUserId`, `recipientUserId`, channel, event type, revision, complete published `data`, provider response, status, duration and result. Async request context preserves the original actor across concurrent fanout and retry awaits. One stable `publicationId` identifies a logical publication to one recipient; `attempt` distinguishes retries. A successful provider response proves publication acceptance, while client receipt is a separate event. Background publications without an originating request use `null` for unknown actor/request IDs. Logging and sink failures never change HTTP results or publication retry behavior.

Open the expandable local viewer and start the manually controlled API with full private capture:

```sh
npm run logs:install  # once
npm run logs          # viewer terminal: http://127.0.0.1:8082/
# In a separate terminal:
npm run start:debug
```

Set `DEBUG_TRAFFIC_LOGGING_ENABLED=false` for metadata-only HTTP logs and no realtime traffic records. Set both flags to `false` to suppress both traffic streams. Application warnings and internal error logs remain separate. The agent does not start or restart the persistent API for you.

Development console output uses compact two-line summaries with UTC timestamps, status/duration and user/request IDs. The optional private JSONL file retains full redacted payloads for Logdy's expandable JSON drawer, filters and JSON/CSV export. Set `TRAFFIC_LOG_FORMAT=json` for the original machine-readable stdout format, `pretty` for summaries or `silent` for file-only traffic capture. `TRAFFIC_LOG_FILE` enables an append-only file; `start:dev` and `start:debug` default it to the workspace's ignored `.runtime/backend-logs/traffic.jsonl`. See [Backend logging](../BACKEND_LOGGING.md) for controls, installation, file bounds and local access protection.

The native file contains only traffic JSON, without npm/Nest startup lines. From the workspace root, find one complete HTTP/fanout flow with `rg '"requestId":"YOUR_REQUEST_ID"' .runtime/backend-logs/traffic.jsonl`. If `jq` is installed, these filters ignore npm/Nest startup lines and read the JSON records:

```sh

jq -R 'fromjson? | select(.event == "http_request" and .userId == "USER_ID")' .runtime/backend-logs/traffic.jsonl
# Publications addressed to one user, including every retry attempt.
jq -R 'fromjson? | select(.event == "realtime_publication" and .recipientUserId == "USER_ID")' .runtime/backend-logs/traffic.jsonl
# HTTP request counts grouped by user, method and route.
jq -Rs '[split("\n")[] | fromjson? | select(.event == "http_request")] | group_by([.userId,.method,.route]) | map({userId:.[0].userId,method:.[0].method,route:.[0].route,requests:length})' .runtime/backend-logs/traffic.jsonl
```

Full debug logs include application message data. Keep local captured files private. For larger searchable collections, [OpenObserve](https://openobserve.ai/docs/getting-started/) provides a self-hosted log-search UI and native single-binary installation. [Loki with Grafana](https://grafana.com/docs/loki/latest/setup/install/local/) is another option. Both can query these JSON fields without changing the HTTP/realtime protocol. The local Logdy viewer supplies expandable inspection and exports; the backend formatter and file sink reuse Node APIs and add no application dependency.

Debug Flutter clients expose the response request ID in the console and Sync diagnostics, so the same ID identifies server completion and fanout records. Enable **Full debug traffic logging** in that panel to inspect client HTTP bodies and received realtime publications, or launch with `--dart-define=DEBUG_TRAFFIC_LOGGING_ENABLED=true`. The backend and client switches are independent; enabling one does not upload logs to the other or to an external service. The client retains only the latest 60 full traffic records and displays counts for that retained window.

For current Redis keys, full room JSON, counters and expiry times, use the separate local [Redis Commander inspector](../REDIS_DEBUGGING.md). It adds no API endpoint or application dependency, and starting it does not start the manually controlled API.

## Reliability, media and capacity follow-up (2026-10-17)

Authentication rejects malformed, expired, unknown-user and retired credentials with 401. MongoDB/Redis authentication lookup failures reject access with retryable 503; a temporary dependency failure must not tell Flutter to clear its saved session or offline drafts. Resource IDs in JSON, query strings and route parameters are normalized before identity comparisons and deduplication.

`POST /presence/offline` atomically writes idempotent retirement and a persistent disconnect retry job independently of the compatibility heartbeat bucket. Separate user/IP logout quotas (30/120 per minute) bound immediate provider work; skipped/failed work remains queued for the bounded background worker without another client request. Redis visibility leases and fenced completion recover API crashes and avoid concurrent ownership; a final pass after 15 seconds catches in-flight connects. Another login for the same account stays valid. Connections use the login's actual expiry with Centrifugo's native expiration grace, and periodic `/internal/realtime/refresh` callbacks are disabled. See [retry and expiry details](../centrifugo/README.md).

`LastSeenService` records approximate `users.lastSeenAt` after the last Centrifugo socket disappears, including an unexpected network disconnect. Its scheduler checks Redis for due users every five seconds. It batches only tracked users every 30 seconds by default (`LAST_SEEN_CHECK_SECONDS`), retains retry state across API restarts, preserves another connected login, and never interprets provider failure as offline. `GET`/`POST /presence/status` return an additive `lastSeenAt` map for permitted offline users only, using the same self/shared-room privacy rules as online status. See [last-seen semantics and OSS webhook limitations](../centrifugo/README.md#last-seen-and-disconnect-notifications).

### Private retained images

`/public/uploads/:filename` keeps the stored path shape but is now an authenticated controller; the static-file bypass is removed. Clients send bearer credentials in headers, fetch bytes and render within their initiating account. Never put access tokens in image query strings. Media responses use `Cache-Control: private, no-store`; unknown and unauthorized files return 404 after authentication. A cancelled response closes its file stream/handle.

A new `uploads` metadata collection stores filename, owner, MIME, byte size, decoded dimensions/frame count, attachment time, orphan eligibility and retained/deleting/deleted state. It has no TTL deletion index. A pending upload is readable and attachable only by its uploader while its metadata state remains retained, including after seven days; orphan eligibility controls explicit cleanup only and never expires durable retries. Attaching it to a message/group avatar marks it attached in the same MongoDB transaction. After attachment, ownership alone never grants access: the caller needs a currently visible, non-globally-deleted message/quote in a room they belong to, a current group-avatar membership, or a current profile-avatar reference for themselves/shared-room peers. A hidden original can still have an authorized visible quote. Unrelated directory users do not gain private avatar access merely by enumerating the directory.

Legacy files without metadata remain readable through those visible references and memberships. Global deletion clears message/quote URLs and revokes new reads when no other authorized reference exists; per-user deletion does likewise for that user's remaining references. Already downloaded bytes cannot be recalled. Server files remain retained, including globally deleted attachments and ambiguous failed uploads. No existing upload migration or deletion is performed.

Uploads remain 5 MiB maximum. Rate limits default to 30/user and 120/IP per minute before Multer body allocation; local request concurrency defaults to four globally and two per user, with a 30-second request deadline. An independent decode permit remains held until work completes even after client cancellation. Sharp fully decodes all accepted JPEG/PNG/GIF/WebP frames and rejects corrupt data, MIME/format mismatches, dimensions above 8,192, more than 60 frames, and total width × height × frames above 16,000,000. This bounds decoded RGBA payloads to approximately 64 MB each, plus native/encoded overhead; concurrency four is a local default, not a measured production memory guarantee. Keep upstream body/time/connection limits aligned when deploying multiple processes.

Inventory retained media with `npm run media:cleanup` from this directory. It defaults to dry-run and prints counts. It never removes attached, referenced, legacy, unknown, symlinked or hard-linked files. Only new metadata-backed uploads that were never attached and passed their configured seven-day eligibility time can qualify. The explicit `npm run media:cleanup -- --apply --confirm-retained-media-cleanup` path claims each candidate against concurrent attachment, rechecks references/inodes and retains deletion metadata; it is an operator action requiring separate authorization. **Apply was not run during implementation or validation.** Attached/deleted-message media retention remains indefinite; changing that retention is a separate policy decision.

### Additive bounded collections

Legacy `GET /users` still returns its full JSON array sorted by display name/ID for datasets within `LEGACY_DIRECTORY_MAX_USERS` (10,000 by default). Above that budget it returns explicit 413 with instructions to use pagination; it never silently omits users. `GET /users?limit=100&afterUserId=<id>` opts into `{users, nextCursor}` sorted by ascending ID; limit is 1–100, and a cursor alone defaults to 100. `nextCursor` is the last returned ID or null. A normal page loads at most limit+1 database rows.

`GET /rooms` retains its unpinned `nextCursor` and legacy all-pinned shape. `pinnedLimit=1..100` opts into bounded pinned rows plus additive `pinnedNextCursor: {beforePinAt,beforePinnedRoomId}|null`. Follow pinned pages with `pinnedOnly=true`, the same pinnedLimit and both pinned cursor fields; those pages contain no unpinned rows and return unpinned `nextCursor:null`. A full-sync client gathers all pinned pages before certifying that snapshot and retains the original server unpinned boundary. Delta-only rooms and later preference changes must never become page cursors. Legacy all-pinned requests fail explicitly above `LEGACY_PINNED_MAX_ROOMS` (1,000). Concurrent mutations remain recoverable through the existing account revision/delta fence; pagination is not a snapshot held across HTTP requests.

### Work deadlines and query plans

MongoDB mutations/revisions still commit together. Post-commit Redis/provider fanout is limited to eight active recipient jobs and 1,000 waiting jobs per process, with a shared ten-second per-mutation fanout deadline. Expired queued jobs are removed before execution. Redis commands have a 1,500 ms response timeout and per-command remaining-deadline timers; upsert/invalidation Lua checks Redis server time before mutation, so delayed or replayed commands cannot apply after their deadline. A timed-out response is ambiguous about work accepted before the deadline; MongoDB revision checks and safe full recovery remain authoritative. Keep backend/Redis clocks synchronized. Cache/provider failures never turn committed sends into failed HTTP mutations. These bounds cover the advisory post-commit lane, not the preceding MongoDB transaction or arbitrary proxy/client network time.

Provider publications retain three attempts with existing backoff, each bounded by `REALTIME_PUBLISH_TIMEOUT_MS` (2,500 default) and the remaining deadline. Queue/deadline exhaustion skips further advisory work; it does not add an outbox or message event log. Test the deployment's workload before adjusting these local defaults.

Around-message context now reads membership, target and neighboring rows in one MongoDB snapshot. Concurrent edits/deletions cannot mix versions inside that response; a response may consistently describe its earlier snapshot, and subsequent requests/client revision recovery observe the new state.

The synthetic 20,000-message explain workload justified four direct-only partial receipt indexes: acknowledged boundary lookups examined one index key/zero documents instead of 2,002/4,002 documents; no-gap checks examined zero keys/documents instead of 1,000/2,000 documents. Two path-only partial image/quote indexes plus explicit string predicates avoid a full message scan for missing media. Startup creates these additive indexes without dropping existing indexes. Their storage/write overhead must be included in production sizing; these local explain results are not a production throughput claim.

Run `npm run build && npm run benchmark:local` only with the local development services. It creates a fresh retained synthetic database/Redis namespace, 100-member group and 20,000-row receipt workload, measures real provider publications with a documented injected 50 ms delay, and exercises an intentionally short advisory deadline. ### Send-queue readiness and errors (2026-10-18)

Public `GET /health` preserves `{status:"ok",mongo:"ok",redis:"ok"}`. `HEAD /health` runs the same checks and returns no body. Both are uncached, probe the MongoDB primary and ready Redis connection concurrently, and bound each driver operation to 1,500 ms. A disconnected dependency or probe failure returns 503 without exposing connection details. These read-only checks do not prove that the next transaction will succeed and do not wait for Centrifugo. Completed 200 GET/HEAD health probes are omitted from HTTP request logs; failed and aborted probes retain normal logging and request correlation.

Problem JSON keeps its existing fields and adds `code` and `retryable`. Validation arrays use `VALIDATION_FAILED`; ordinary 400s use `BAD_REQUEST`. Other stable categories include `AUTHENTICATION_REQUIRED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `PAYLOAD_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, `RATE_LIMITED`, `INTERNAL_ERROR` and `SERVICE_UNAVAILABLE`. Unknown categories use `HTTP_<status>`; clients must accept future codes and must also handle proxy failures without JSON. Only 408, 429, 500, 502, 503 and 504 are marked retryable. This is a scheduling hint for an idempotent request: retain its original identity, apply capped backoff and preserve ambiguous sends. A false hint does not authorize dropping a pending message; pause it for correction or reauthentication.

429 responses retain `Retry-After: 60` and add matching `retryAfterSeconds:60`. CORS exposes `Retry-After` and `X-Request-ID`, including for Flutter Web. Validation failures remain 400/nonretryable, with request metadata logging that does not include message content outside the separately enabled development traffic logger. Existing send idempotency, transaction sequence allocation, upload paths and attachment lifecycle are unchanged.
